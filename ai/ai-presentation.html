¿Qué es un AI Coding Agent?

Un LLM solo produce texto.

Un AI Coding Agent le da agencia (capacidad de actuar solo) a través de un harness: le expone tools (leer, escribir, correr comandos) y corre un loop (actúa, ve el resultado, corrige...)

Ejemplos

  • Claude Code
  • Codex
  • Opencode
  • Pi (por lejos, el mejor)

Ponytail: cómo programa el Agente

Antes de escribir una linea de codigo, el agente para en el primer paso que se cumple:

  1. Does this need to exist? → no: skip it (YAGNI)
  2. Already in this codebase? → reuse it, don't rewrite
  3. Stdlib does it? → use it
  4. Native platform feature? → use it
  5. Installed dependency? → use it
  6. One line? → one line
  7. Only then: the minimum that works

Comandos

  • /ponytail — cambiar intensidad (lite/full/ultra)
  • /ponytail-review — pr-review anti over-engineering
  • /ponytail-audit — audita todo el repo
  • /ponytail-debt — juntar los TODOs marcados ponytail:
🪨

Caveman: cómo habla el Agente con nostoros

Prosa sin chamuyo

  • Respuestas concisa
  • Sin resúmenes al final
  • Sin explicar lo obvio del diff

Ejemplo

Prompt

"¿Cómo agrupo una List en un Map por una key usando type classes en Scala?"

Normal

"Podés modelarlo con una type class Groupable[A, K] y derivar la instancia con Shapeless; después usás foldLeft sobre un Map inmutable con un Semigroup del cats para combinar los valores, o directamente groupMapReduce si estás en 2.13+. Total abstracción, cero mutación, todo referencialmente transparente..."

Caveman

"Usá Java."

Ejemplo (real, en Java)

Prompt

"¿Cómo agrupo una List en un Map por una key en Java?"

Normal

"Tenés varias opciones. Podés hacer un for con computeIfAbsent, o lo idiomático desde Java 8: Collectors.groupingBy, que arma el Map<K, List<V>> directo. Incluso le pasás un downstream collector como counting() o mapping()..."

Caveman


list.stream().collect(Collectors.groupingBy(V::key));

Comandos

  • /caveman — cambiar intensidad (lite/full/ultra)
  • /caveman-commit — mensaje de commit terse
  • /caveman-review — review de 1 línea por finding
  • /caveman-stats — tokens ahorrados + USD

RTK: minimiza los tokens que lee el Agente por Bash

Comprime el output antes de que el Agente lo lea, hasta 90% menos (supestamente).


git push

antes


Enumerating objects: 5, done.
Counting objects: 100% (5/5), done.
Delta compression using up to 8 threads
...

después


ok main

¿Cómo se engancha?

Se mete antes de cada comando de shell:


PreToolUse(Bash)   # antes de correr un comando

Y lo reescribe para comprimir el output:


git status         # lo que pide el agente
rtk git status     # lo que corre en realidad

Hooks

Scripts que el agente corre de manera deterministica y automática en puntos discretos del ciclo de vida de una sesion.

Anatomía

Un hook = evento (cuándo) + matcher (qué lo dispara) + tipo (qué ejecuta).

Eventos

EventoMatchea contra
SessionStartsource (startup, resume…)
UserPromptSubmit—
PreToolUse nombre del tool
PostToolUsenombre del tool
Stop—
PreCompacttrigger (manual, auto)
SubagentStart/Stoptipo de agente
SessionEndreason (clear, logout…)

El matcher se escribe como regex (Edit|Write, mcp__jira__*)

Tipos

Lo que el evento + matcher dispara:

TipoQué ejecuta
commandcorre un script bash local
httpejecuta una request
mcp_toolllama un tool de un MCP ya conectado
promptle pregunta a un modelo rápido sí/no
agentlanza un subagente que verifica algo más complejo

Dónde está definido

En ~/.claude/settings.json:


"hooks": {
  "PreToolUse": [
    {
      "matcher": "Bash",
      "hooks": [
        { "type": "command", "command": "rtk hook claude" }
      ]
    }
  ]
}

settings.json

El archivo de config declarativa del agente.

Los 4 scopes

ScopeArchivoA quién afectaPara qué
User ~/.claude/settings.json Vos, en todos los proyectos de esta máquina Preferencias personales: theme, editor mode, modelo default, tus reglas de permisos, hooks personales
Shared project .claude/settings.json Todos los que abren el agente en esa carpeta. Se commitea Permisos del equipo, hooks, plugins y env vars del proyecto
Project local .claude/settings.local.json Vos, solo en este proyecto. Se gitignorea Overrides personales de un proyecto
Managed managed-settings.json y otras fuentes de la org Todos los de la orga, nada le gana Política de seguridad y compliance

Precedencia (gana sobre): managed ▸ command line ▸ project local ▸ shared project ▸ user. Entre los tuyos gana el más específico; managed se impone siempre.

Qué podés configurar

Cada campo del archivo controla una parte distinta del agente:


{
  "model": "...",
  "permissions": { },   // qué se auto-aprueba / bloquea
  "hooks": { },         // scripts en el ciclo de vida
  "statusLine": { },    // la barra de estado
  "env": { },           // variables de entorno
  "enabledPlugins": { } // ponytail, caveman...
}

Status Line

Un script tuyo que el agente corre en cada render, pasándole el estado de la sesión por stdin.

Qué te muestra


model.display_name       # modelo activo
context_window.*         # tokens usados / %
session.cost_usd         # costo acumulado
session.total_lines_*    # líneas agregadas / borradas
vim.mode                 # insert / normal
output_style.name        # ponytail, caveman…
workspace.current_dir    # carpeta actual
gitBranch                # branch (armado en el script)
etc

context_window.* es clave: una sesión para una sola tarea, idealmente sin pasar el 40% del context window.

Cómo se configura

En settings.json apuntás a tu script:


"statusLine": {
  "type": "command",
  "command": "~/.claude/statusline.sh"
}

O más fácil: pedile a Claude que te la configure — /statusline arma el script solo.

CLAUDE.md

Instrucciones en markdown que el agente lee al inicio de cada sesión.

Es un prompt más → probabilístico

Los mismos 4 scopes

Mismas reglas que en settings.json:


managed   /etc/claude-code/CLAUDE.md   # org
user      ~/.claude/CLAUDE.md           # todos tus proyectos
project   ./CLAUDE.md                   # commiteado, equipo
local     ./CLAUDE.local.md             # gitignored, solo vos

Buenas prácticas

Que sea conciso y legible para humanos (a lo sumo 200 líneas).

✅ Poner

  • Comandos comunes usados: testear, compilar, linter
  • Ejemplos de código antes que explicaciones
  • Estilo del repo (nombres de branch, convenciones de PR, convenciones de codigo)
  • Comportamientos no obvios

❌ No poner

  • Lo que el agente puede deducir leyendo el código
  • Documentación detallada de API (linkeá a los docs)
  • Info que cambia seguido
  • Obviedades tipo "escribí código limpio"

Ejemplos

  • ✅ Bueno: allaria-chat/.claude/CLAUDE.md
  • ❌ Malo: multica-ai/andrej-karpathy-skills

Comentarios para humanos

Los HTML comments del CLAUDE.md no son leidos por el agente

Skills

Un workflow empaquetado que el agente carga on-demand, o que vos ejecutás a mano.

Anatomía

Un SKILL.md = instrucciones + (opcional) tools + (opcional) scripts.

Lo mínimo es definir un frontmatter con name + description, y las instrucciones abajo.


---
name: explain
description: Explica un concepto como si fuera de Boca
---
Explicá $ARGUMENTS en 3 bullets muy muy muy muy simples.

Dónde definirlas

Mismos 4 scopes que settings.json y CLAUDE.md:


~/.claude/skills/<nombre>/SKILL.md   # user, todos tus proyectos
.claude/skills/<nombre>/SKILL.md      # project, commiteado

Ejemplos

  • grill-me: te interroga sobre el plan hasta resolver todo
  • to-questionnaire: convierte preguntas que no podes responder en un cuestionario para Producto
  • improve-codebase-architecture: busca mejoras de arquitectura
  • teach: te enseña un tema usando el repo como workspace
